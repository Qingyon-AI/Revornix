# Quick Start

<Callout>
	If you want to try the product directly first, go to <a href='https://app.revornix.com'>https://app.revornix.com</a>.
	**Users in mainland China should prefer the local mirror <a href='https://app.revornix.cn'>https://app.revornix.cn</a> for a more reliable connection.**
	This page is mainly for local/self-hosted deployment.
</Callout>

<Callout>
	If your main business services run in mainland China but you still need Google / GitHub login, also read [Gateway Deployment](developer/gateway) so the public entrypoint and overseas auth API are planned together.
</Callout>

## Manual Deployment Method

<Callout>
	The Python side uses [uv](https://docs.astral.sh/uv/): `api` and `worker` are two members of a single uv workspace, sharing one `uv.lock` and one `.venv` at the repo root. There is no need for a separate environment per service — both dependency sets come out of the same resolution, so they cannot conflict. uv also downloads the matching Python itself, so none needs to be preinstalled.
</Callout>

<Steps>

### Clone the repository to your local machine

```shell
git clone git@github.com:Qingyon-AI/Revornix.git
cd Revornix
```

### Install and start the foundational services

<Callout>
	If you do not already have Postgres, Redis, Neo4j, MinIO, and Milvus running, use `docker-compose-local.yaml` together with `.env.local.example` to bootstrap the local infrastructure layer.
</Callout>

<Callout type='warning'>
	Note: If some of these dependencies are already running on your machine, disable the corresponding services in `docker-compose-local.yaml` to avoid port conflicts and accidental data mixups.
</Callout>

Copy the example file and adjust it together with the [environment guide](environment). In the simplest local setup, the most important custom value is usually `OAUTH_SECRET_KEY`.

```shell
cp .env.local.example .env.local
```

Start the local infrastructure services.

```shell
docker compose -f ./docker-compose-local.yaml --env-file .env.local up -d
```

### Configure environment variables for each microservice

```shell
cp ./web/.env.example ./web/.env
cp ./api/.env.example ./api/.env
cp ./worker/.env.example ./worker/.env
cp ./gateway/.env.example ./gateway/.env
```

`hot-news` does not currently ship a committed `.env.example`, so if you want custom configuration there, create `hot-news/.env` manually according to the variables described in the [environment guide](environment).

Update each service's env file as needed. For details, see the [Revornix Environment Variables section](environment).

<Callout type='warning'>
	If you deploy manually, `OAUTH_SECRET_KEY` must be identical across API and Worker; otherwise, the authentication and internal service trust chain will break.
</Callout>

### Start the core backend service

<Callout type="info">
No manual database initialization. Every API startup runs an idempotent pass that creates
tables, applies column migrations, seeds built-in data and ensures the Milvus collection
exists — fresh installs and upgrades alike need nothing but starting the service.
</Callout>

`app/`, `api/` and `worker/` form a uv workspace: one `uv.lock`, one `.venv` at the repo
root, shared by both Python services. Install once, from the **repo root**:

```shell
uv sync --all-packages
uv run --directory api fastapi run main.py --port 8001
```

<Callout type="warn">
`--directory` is not optional. The log path and which `.env` gets read are both resolved
from the working directory; running from the repo root picks up the root config instead —
no error, just the wrong values.
</Callout>

### Start the hot-search aggregation service

```shell
cd hot-news
pnpm install
pnpm build
pnpm start
```

### Start the Celery task queue

```shell
uv run --directory worker playwright install chromium-headless-shell
uv run --directory worker celery -A common.celery.app worker \
  --pool=threads --concurrency=20 --loglevel=info -E
```

### Start the frontend service

```shell
cd web
pnpm install
pnpm build
pnpm start
```

### Start the gateway service (optional)

```shell
cd gateway
go run ./cmd/gateway
```

</Steps>

Once all services are running:

- The frontend entrypoint is always http://localhost:3000
- If you enable the gateway, use it for backend traffic splitting such as API / Hot News (for example http://localhost:8787)
- If you do not enable the gateway, update `web/.env` so `NEXT_PUBLIC_API_PREFIX`, `NEXT_PUBLIC_NOTIFICATION_WS_API_PREFIX`, and `NEXT_PUBLIC_HOT_NEWS_API_PREFIX` point directly to backend services
